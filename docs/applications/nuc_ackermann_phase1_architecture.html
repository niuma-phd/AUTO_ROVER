1. 当前整体阶段

软件侧的 Phase-1 已知地图闭环和正式的进程内 Wheeltec 后端候选已经实现并通过完整测试；当前车辆牵引电源、激光雷达均关闭，VCU 仅由 NUC USB 供电。现阶段能安全完成的软件、静态审计和只读观测已经完成，真实写串口与车轮执行仍被刻意阻止。

2. Phase-1 任务边界与不变量

本阶段要做

  • Ubuntu 20.04、ROS 1 Noetic 上的已知航点导航。
  • 把外部定位转换为后轴中心 EgoState。
  • 把版本化 RoutePlan 生成可执行 Trajectory。
  • Pure Pursuit 产生期望 MotionReference。
  • 由安全监督、命令 guard、运动管理器和选定 VCU 后端共同决定是否执行。
  • 终点受控减速、确认静止并 STOP_AND_HOLD。

明确不做

  • 无 Phase-1 world model、在线障碍检测、局部避障或在线重规划。
  • 无自动探索、覆盖规划或运行时任务管理器。
  • 不在本阶段维护 ROS 2 空壳；未来是原生移植。
  • 不把厂家 VCU 协议泄漏进 planning/control。
  • 不把软件急停冒充物理独立急停链。

3. 总体架构与闭环数据流

ROS 只存在于图的边缘。领域类型、几何、规划、跟踪、安全和车辆状态机是普通 C++ 核心；ROS wrapper 只做参数、消息、服务、时间接收和显式转换。

  1. 路线入口：当前没有一个“off-board RoutePlan ROS 发布节点”。waypoints.yaml 被 route_planner_node 严格解析成核心域 RoutePlan，再生成并周期发布 /trajectory。
  2. 定位入口：FAST-LIVO2 的 /aft_mapped_to_init（nav_msgs/Odometry）经过固定外参数值合成，输出后轴中心 /ego_state；不查询或广播 TF。
  3. 跟踪：Pure Pursuit 同时要求新鲜、有效、有序的 Trajectory、EgoState、ChassisState 和 SafetyState，然后输出 /motion_reference。
  4. 执行决策：车辆执行核心再次验证全套输入，SafetySupervisor 给出模式，CommandGuard 给出受控参考，VehicleMotionManager 生成带序号与单调时钟 deadline 的 VehicleExecutionCommand。
  5. 后端：VehicleExecutionCommand 通过进程内 C++ VehicleBackend 接口送到 FakeVcu 或 Wheeltec 后端；它没有对应 ROS 消息，不暴露公共 bypass topic。
  6. 反馈闭环：后端归一化反馈为 /chassis_state；车辆执行发布 /safety_state。两者同时返回 tracker，防止“控制器不知道软件是否已授权”的死锁或越权。

4. 十个功能包与依赖职责

依赖方向始终从应用边缘流向可复用核心：planning 不依赖定位实现或 VCU；control 不依赖 VCU；adapter 不含轨迹跟踪；底层包不依赖 bringup。

1 · auto_rover_core

角色：ROS 无关的领域类型、几何、角度/位姿运算和合同校验。

关键值：EgoState、RoutePlan、Trajectory、MotionReference、ChassisState、SafetyState、VehicleProfile、进程内 VehicleExecutionCommand。

节点：无。它是其余算法包的最底层。

2 · auto_rover_interfaces

角色：ROS 1 Noetic 公共合同源码，只含消息和服务定义。

9 个消息：ChassisState、EgoState、EmergencyStop、MotionReference、RoutePlan、RouteWaypoint、SafetyState、Trajectory、TrajectoryPoint。

4 个服务：ArmVehicle、AssertEmergencyStop、ReloadRoute、ResetEmergencyStop。

3 · auto_rover_ros1_conversions

角色：ROS 消息与核心域类型的一一显式转换，处理枚举、时间、姿态、valid mask 与不可用字段。

边界：转换本身不证明 freshness；订阅 wrapper 另外记录本机单调 receipt time。

节点：无。

4 · auto_rover_localization

角色：FAST-LIVO2 nav_msgs/Odometry 到后轴中心 EgoState 的薄适配。

节点：fast_livo_odometry_node / fast_livo_odometry_adapter。

严格项：审计过的 source revision、camera_init/aft_mapped、递增 stamp、receipt freshness、已知归一化外参。真实配置的外参和 freshness 仍故意无效，所以当前实机启动会 fail closed。

5 · auto_rover_planning

角色：严格且有编译期资源上限的 YAML 航点加载、路线版本仓库、Hermite 轨迹生成与曲率可行性验证。

节点：route_planner_node / route_planner。

输出：确定性 trajectory identity、弧长、yaw、曲率、速度与 STOP_AND_HOLD 完成语义；输入和输出资源边界与车辆执行端对齐。

6 · auto_rover_control

角色：ROS 无关 Pure Pursuit 跟踪器与薄 wrapper。

节点：pure_pursuit_node / pure_pursuit。

输出：只产生期望 MotionReference；它不是执行授权，更不了解串口、Wheeltec 或 /cmd_vel。

7 · auto_rover_safety

角色：SafetySupervisor 与 CommandGuard 两个 ROS 无关核心。

能力：启动 inhibit、连续新鲜恢复、显式 arm、故障撤权、锁存软件 E-stop、授权且 generation 匹配的 reset，以及输入 freshness/validity/限值/方向检查。

节点：无；被车辆执行进程组合。

8 · auto_rover_vehicle

角色：VehicleExecutionCore、VehicleMotionManager、通用 VehicleBackend 接口与确定性 FakeVcu。

节点：vehicle_execution_node / vehicle_execution（fake 后端组合）。

关键边界：唯一生成 VehicleExecutionCommand 的地方；启动、故障、重连、E-stop、异常和退出都会撤销授权并尝试显式零命令。

9 · auto_rover_vcu_wheeltec_serial

UNVERIFIED

角色：原创的候选 codec、流 parser、物理 transport、activation、adapter watchdog、runtime、VehicleBackend 和正式 ROS wrapper。

节点：wheeltec_vehicle_execution_node / wheeltec_vehicle_execution。另有 receive-only 与实验台架工具，但它们不接入导航图。

状态：注入/PTY 路径通过；真实 actuation 编译门为 false。

10 · auto_rover_known_map_bringup

角色：NUC Ackermann 已知地图应用组合，拥有车辆 profile、路线、控制、定位和安全配置，以及最小 launch。

测试夹具：fake_fast_livo_source.py 根据 fake chassis feedback 积分位姿，形成确定性软件闭环。

边界：它不是可复用算法包，不提供探索/覆盖模式切换。

6. 路线、轨迹、定位与 Pure Pursuit

6.1 当前 RoutePlan 如何进入系统

当前入口是应用包中的 config/waypoints.yaml，不是在线规划器和 ROS RoutePlan topic。严格 loader 只接受 schema v1 的完整键集：

schema_version: 1
frame_id: camera_init
route_id: commissioning_route_01
plan_version: 1
loop: false
waypoints:
  - {x_m: 0.0, y_m: 0.0, yaw_rad: 0.0, speed_mps: 0.50}
  - {x_m: 2.0, y_m: 0.0, yaw_rad: 0.0, speed_mps: 0.50}

未知键、缺失键、重复键、非有限数、少于两个点、重复位置、错误 frame、非正版本、负速度、超限速度、reverse 或不合法路线都会拒绝。RouteRepository 还防止同一路线版本回退或同版本内容改变。

6.2 Planning 资源边界（ADR 0006，Proposed）

ADR 0006 当前状态是 Proposed，不是 Accepted。它把操作员可编辑路线当作可能最终请求运动的车载输入，在调用 yaml-cpp、分配航点、做重复位置比较、哈希和 Hermite probe 之前先限制工作量。所有上限都是公共 ROS-free header 中的编译期安全合同，不能由 launch 或 YAML 放宽，也不会截断超限内容。

6.3 轨迹生成

几何

  • 相邻航点由二维 cubic Hermite 段连接。
  • 先做密集 feasibility probe，再按 0.05 m 分辨率采样。
  • 计算切向 yaw、解析曲率、累积弧长并拒绝零切线/重复采样。
  • 曲率全程必须满足 |κ| ≤ 1 / 0.95。

语义与资源界限

  • 速度在航点间插值，方向固定 FORWARD。
  • trajectory identity 由路线、profile 和配置的确定性 fingerprint 构成。
  • 带 route_id、plan_version、valid_for、vehicle_profile_id。
  • 完成语义固定为 STOP_AND_HOLD；执行边界最多接收 4096 点。

6.4 定位转换

定位核心执行明确乘法顺序 world_T_rear = world_T_source × source_T_rear。它验证 camera_init、aft_mapped、审计过的 FAST-LIVO2 revision、递增 provider publish stamp、单调 receipt freshness、有限位姿和归一化外参四元数。FAST-LIVO2 stamp 目前被标注为 publish time，不是传感器 sample time；代码不会伪造 twist、covariance 或 sample timestamp。

6.5 Pure Pursuit

步骤当前实现安全结果
输入门四个输入必须 valid、receiver-fresh、producer-valid、身份/时间有序；trajectory 与 profile 合同必须一致。任一失败输出 invalid exact-zero，并清除斜坡授权。
软件授权所有非 ARMED 的有效 SafetyState 输出 valid exact-zero；第一次 ARMED 更新也只建立零斜坡原点。避免从未知旧速度直接起步；软件授权不伪造 VCU enable。
VCU enable 能力若 chassis 从未提供 CONTROL_ENABLED_VALID，ARMED 可形成参考；若该 bit 存在但 false，则保持零；同一 source 一旦提供后又消失，fail closed。兼容 Wheeltec “能力不可证实”，同时不把 FlagStop 当 enable。
进度只从当前 progress index 向后搜索最近点，防止正常运行时回跳。trajectory/source identity 回退或 retired generation replay 被拒绝。
动态前视L = clamp(0.40 + 0.50·|v_measured|, 0.40, 0.80) m。目标点必须在车辆局部 +x 前方，否则失效关闭。
曲率κ = 2·y_local / (Δx² + Δy²)，正值左转。非有限或超过 1/0.95 m⁻¹ 立即拒绝。
减速v_stop = sqrt(2·a_max·remaining_distance)，与轨迹速度取最小，再做 0.20 m/s² 双向斜率限制。到达 0.08 m 位置阈值后继续减到零，只有实测速度 ≤0.01 m/s 才报告 route complete。

7. 安全状态机与双重 watchdog

非零运动不是由一个布尔参数决定，而是由状态机、输入健康、明确 operator arm、命令 generation/deadline、后端连接与适配器本地授权共同满足。任一层失败都会撤权并进入显式零命令路径。

安全职责分层

SafetySupervisor

拥有 boot/recovery/disarmed/armed/fault/E-stop latch 模式；arm 必须携带当前 state generation。E-stop generation 单调增长，复位不直接进入运动。

CommandGuard

独立验证 Ego、Trajectory、MotionReference、ChassisState、SafetyState 的 receipt freshness、声明有效期、身份顺序、车辆 profile、方向和限值；恢复要求连续新命令。

VehicleMotionManager

把 guard 结果变成有 sequence、created monotonic time、absolute deadline、motion_enabled、hold 和 stop_reason 的执行命令；连接 generation 或授权变化会清除旧命令。

双 watchdog 与失败语义

  • 上游 watchdog：CommandGuard 以本机单调 receipt time 检查各输入 age，同时检查 ROS/source stamp 声明的 valid_for。
  • 适配器 watchdog：VCU 后端独立检查 VehicleExecutionCommand age、deadline、sequence、连接 generation、本地授权时间与最大输出间隔；不依赖 ROS callback 是否继续运行。
  • 恢复：正常超时后不能用一帧“好消息”立即恢复；fake 配置和候选 Wheeltec 配置均要求连续新鲜命令/反馈。
  • 停止交付：链路可写时做有界零写；断开、部分写或超时会报告 delivery_unconfirmed，绝不把 OS write 当成 VCU ACK 或物理停车证明。
  • 独立硬件链：软件 E-stop 只是一条进程内锁存路径。物理急停、断电、制动/驻车仍须由车辆侧独立实现并验收。

8. Wheeltec：从 ROS 到串口的九层责任与候选帧

下面的“九层”是按当前实现责任从上到下展开的解释口径。每层只处理自己的问题，尤其不能把协议字段直接送进 tracker，也不能绕过共享车辆执行核心。

九层逐层说明

#层主要责任失败时
1ROS wrapper订阅/服务/转换、输入资源上限；物理 worker 与 ROS callback 分离。callback/backend 异常、deadline miss、mailbox contention 或超大输入触发 poison-aware stop 并终止节点。
2VehicleExecutionCore与 fake 完全共用的 SafetySupervisor、CommandGuard 和 MotionManager。撤销 authorization epoch，生成/尝试零命令，不让 adapter 直接接 tracker。
3VehicleBackend把通用 health/poll/deliver/revoke/shutdown 语义映射到 Wheeltec runtime。把后端断开/watchdog/未确认交付映射为通用 StopReason。
4Runtimestartup zero、清 backlog、running、反馈 freshness、FlagStop 本地 inhibit、连接 generation。断开为 terminal；普通撤权可在健康 session 内有界停机，但不会自动恢复旧授权。
5Adapter检查命令 sequence、created/deadline、age、codec limit、双授权、连接 generation；需要连续新鲜命令恢复。清除缓存运动，进入有界 exact-zero episode；部分/失败写保持 delivery unconfirmed。
6Codec定宽整数、向零截断、前向/横向/yaw 映射、XOR、范围与曲率检查。NaN/Inf、reverse、横向非零、零速非零 yaw、超速/超曲率/溢出均在 write 前拒绝。
7Stream parser在碎片和噪声流中寻找 24B header/tail/XOR/二值 FlagStop 合法候选。丢一字节继续搜索；坏帧绝不刷新有效反馈 watchdog。
8Physical activation任何 write-enabled 调用者在首次读/普通命令前共同执行十个 0x00 padding + exact-zero。任何 partial/unknown prefix 都从完整 padding 重启；次数/deadline 有界，绝不尝试非零。
9Physical open/transport直接 /dev 路径、character TTY、major/minor/inode、owner/group/mode、USB VID/PID/serial、flock、TIOCEXCL、115200 8N1 readback 与 deadline I/O。任一不匹配 fail closed；当前 actuation 模式更早被不可配置的编译门拒绝。

候选 11 字节命令帧

字节候选语义编码规则
0header0x7B
1–2reserved固定 0x00 0x00
3–4forward speed有符号 int16，大端，m/s × 1000，向零截断
5–6lateral speed有符号 int16，大端；Ackermann Phase-1 必须为 0
7–8yaw rate有符号 int16，大端，rad/s × 1000；候选映射为 speed × curvature
9checksumbytes 0…8 的 XOR
10tail0x7D

exact-zero 候选为 7B 00 00 00 00 00 00 00 00 7B 7D。但是，供应固件的 UART parser 使用跨 Linux close/reopen 保留的函数静态半帧计数，所以“主机写完一个完整 zero frame”并不证明 MCU 从帧边界开始解析。ADR 0003 的软件证明因此采用 10 个零 padding + exact-zero，覆盖 parser count 0…10；截至本文档时间，该序列仍未发送到真实 VCU。

字节候选语义注意

2–7forward / lateral / yaw三个有符号 int16，大端，除以 1000。
8–13三轴 acceleration三个有符号 int16，除以 1671.84。

反馈缺失的事实：帧中没有已观察到的 VCU source timestamp、sequence、command echo、controller ACK、可归一化的 control-enabled 或具体 fault provenance。wrapper 只能标注本机 receipt time；完整 OS 写入只能证明字节到达主机传输边界。

  • NaN/Inf、未知 schema/enum、错误 valid mask、reverse/gear、曲率和速度边界。

10. 物理未闭合项与下一阶段最短路径

当前“车辆和 LiDAR 断电、VCU USB 供电”的条件下，能做的只读捕获、主机枚举、代码闭环、parser 软件证明和 transport race 测试已经完成。下列事实必须逐项留证，不能用参数修改替代。

优先级验收项当前状态闭合证据
1Installed firmware 身份BLOCKED USB WCH bridge 身份不是 STM32 image 身份。经授权的 SWD/JTAG/vendor read-back 或固件自身认证报告，绑定硬件 subtype、image hash/build、Flash 参数和车辆模式。
2牵引能量独立隔离下 parser resyncUNVERIFIED 10×00 + exact-zero 只在软件/PTY 证明。断路器打开、独立确认 actuator energy isolated；从 retained count/干扰前缀验证零-only sequence，记录原始字节和完整/部分写结果。
3Unclean restartUNVERIFIED SIGKILL/断连可留下未知半帧。对正常退出、kill、拔插、host reboot、VCU reboot 做序列化测试；每次都不重放旧命令，恢复需新 generation、连续反馈、显式 re-arm。
4Transport ownershipUNVERIFIED 当前设备 root:dialout 0660 且无 holder，但两条旧规则仍请求 0777。管理员移除/加固旧 udev 规则；专用 service identity、受限组成员、禁用竞争厂家服务、每次 pre-open holder audit。
5Post-open USB 绑定BLOCKED devtmpfs 三向 identity 仍不能覆盖所有 hotplug/device-number reuse race。allocation-free 的 post-open sysfs-object USB VID/PID/serial 绑定，或等价、经审查的不可替换身份机制。
6Controller watchdog 与 loop ownershipUNVERIFIED 候选固件 SecurityLevel=1 可能在 UART 丢失后保留最后目标。识别 installed 配置；测量命令丢失后的 controller 行为、timeout 和安全输出；若无可靠 watchdog，书面批准补偿控制和残余风险。
7外部断电 / E-stop / restart durabilityBLOCKED 软件 latch 在进程内，不证明重启前断言；硬件独立链未验收。记录物理断电链对 VCU/执行器的作用与反馈；采用独立外部或 durable latch 策略，分别批准 readiness 与 safety disposition。
8制动、holding 与 ground loadedUNVERIFIED 架空轮 tail 不是制动距离/驻车能力。受控地面验证普通减速、失联、零命令、断电、坡面保持、方向符号、转向 R≥0.95 m 和 0.50 m/s 目标前的 go/no-go。
9FAST-LIVO2 实机BLOCKED LiDAR 当前断电，真实 config 故意 fail closed。测量 source/IMU→rear-axle 外参、发布频率/抖动、source-to-publish 延迟、一会话 world frame；随后做 known-map 路线验收。

建议执行顺序

  1. 仍不加牵引电：获取 installed firmware 身份方案和独立能量隔离检查方法；管理员清理 ownership/udev；补 post-open USB 绑定实现与测试。
  2. 断路器打开、执行器能量独立确认：按已接受 ADR 0003 做专用 zero-only parser resync 与 unclean restart 证据。此阶段仍不得发送非零。
  3. 架空并受控上电：确认物理 E-stop、控制器 watchdog、启动自检风险、command ownership、braking/hold 和符号；只有 reviewed go/no-go 后才讨论编译门变更。
  4. 激光雷达上电：测外参、rate/jitter/latency 与 session frame；把实测值写入版本化 config。
  5. known-map 验收：先架空轮/台架，再受控地面；保持 0.50 m/s、0.20 m/s²、R≥0.95 m、禁止倒车和独立物理 E-stop。
编译门变更条件：在 installed firmware、parser/restart、ownership、watchdog、外部/durable E-stop、制动/holding 与地面控制等证据被审查前，kPhysicalActuationReleaseEnabled 必须保持 false。本 HTML 不构成打开该门的授权。

12. 最终如何实现整个任务

当物理门逐项关闭并获得正式放行后，系统完成一次已知路线任务的运行链如下。它没有隐式模式切换，也没有绕过安全边界的快捷通道。

  1. 准备路线：操作员在 waypoints.yaml 中给出同一 camera_init 会话下的已知航点、yaw 和不超过 0.50 m/s 的前向目标，并提高 plan_version。
  2. 建立定位：FAST-LIVO2 发布 /aft_mapped_to_init；定位 adapter 用实测 source_T_rear 转成后轴中心 /ego_state，保留 publish-time 和 receipt-time 的差异。
  3. 生成轨迹：route planner 把 YAML 解析为域内 RoutePlan，验证 schema/frame/version/profile 后生成曲率可行的 Hermite /trajectory。
  4. 建立健康状态：后端反馈 /chassis_state；VehicleExecutionCore 在启动零状态下观察 Ego/Trajectory/Motion/Chassis 和后端 health，积累连续新鲜恢复样本，发布 DISARMED /safety_state。
  5. 显式授权：操作员带当前 safety generation 调用 /arm_vehicle。第一次 ARMED controller update 仍输出零，只建立新的加速度斜坡原点。
  6. 跟踪：Pure Pursuit 选动态前视点，算后轴曲率与停车速度，以 0.20 m/s² 斜坡产生 /motion_reference；CommandGuard 再次检查 freshness、限值、方向、身份与 SafetyState。
  7. 执行：VehicleMotionManager 形成进程内 VehicleExecutionCommand。所选后端检查自己的 generation/deadline/watchdog；Wheeltec adapter 才在最外层把它变成候选 11B 串口帧。
  8. 闭环与停止：底盘反馈回到 ChassisState、定位和 tracker；终点按剩余距离减速，实测静止后 route_complete=true 并持续 exact-zero/hold。故障、过期、断开、E-stop 或重启都撤权，不自动恢复旧运动。
一句话总结：规划负责“想走哪条几何路线”，控制负责“希望以多大速度和曲率跟踪”，安全/车辆执行负责“现在是否允许、以什么受限命令执行”，VCU adapter 只负责“如何把已检查命令变成特定协议并把反馈归一化”。这四种责任没有混在一起。
